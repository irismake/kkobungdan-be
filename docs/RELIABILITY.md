# 신뢰성 가이드

## 목표

백엔드는 핵심 생명주기 전반에서 상태 무결성을 지켜야 한다.

- 요청서 공개
- 제안 생성과 수락
- 미션 진행
- 결제 상태 변경

## 기본 기준

- 상태 전이는 서버에서 검증해야 한다.
- 쓰기 작업은 트랜잭션으로 보호되어야 한다.
- 외부 실패는 예측 가능한 에러 코드로 드러나야 한다.
- 로그에는 실패한 리소스와 전이 정보가 식별 가능하게 남아야 한다.

## 주요 실패 모드

- 중복 제안 수락
- 미션 상태와 결제 상태의 불일치
- 재시도 요청에서의 멱등성 공백
- 상태 변경 경로의 권한 검증 누락

## 백업과 복구

DB는 EC2 한 대 안의 MySQL 컨테이너다. 관리형 DB의 자동 백업·시점 복구가 없으므로 아래 백업이 복구 수단이다.

- **백업**: systemd timer가 `mysqldump → gzip → S3`(`kkobungdan-db-backup/mysql/<env>/`)를 돌린다. PROD는 매시 `:05`,
  STAGING은 매일 03:30 KST. 끝까지 쓰이지 않은 덤프는 올리지 않는다(`gzip -t`, `-- Dump completed` 확인)
- **보관**: S3 수명주기 약 30일. EC2 로컬 사본은 PROD 1일, STAGING 3일. EC2 역할에는 S3 삭제 권한이 없다
- **복구 목표(RPO)**: PROD는 최대 약 1시간, STAGING은 최대 24시간의 데이터 손실을 감수한다
- **실패 알림**: 백업이 실패하거나 디스크 사용률이 85% 이상이면 Slack으로 알린다
- **복원 테스트**: S3 최신 백업을 같은 서버의 임시 DB에 복원해 행 수·내용 해시를 운영 DB와 비교하고 임시 DB를 지운다.
  월 1회 이상 한다. 절차는 [`2026-09-29-rds-to-ec2-mysql.md`](./exec-plans/completed/2026-09-29-rds-to-ec2-mysql.md) 6.6
- **단일 호스트**: EC2가 멈추면 앱과 DB가 같이 멈춘다(TD-013)

## 검증 기대치

- 권한 경계에 대한 API 수준 검증
- 과거 실패 흐름에 대한 명시적 회귀 검증
