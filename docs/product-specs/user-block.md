## 범위

- 차단 구현은 채팅과 별도 브랜치에서 한다. 차단 기록용 테이블을 따로 만든다.
- 차단이 채팅에 주는 영향의 세부 규칙(채팅 전송 거부, 채팅방 응답의 차단 여부, 실시간 반영)은 [`chat-requirements.md`의 사용자 차단 상태](./chat-requirements.md#사용자-차단-상태)를 따른다.

## 핵심 원칙

차단은 채팅방이나 요청 단위가 아니라 **사용자 간 관계**로 관리한다.

A가 B를 차단하면 두 사람 사이의 모든 채팅방에서 일반 채팅이 제한되고, 새로운 지원도 양방향으로 제한된다. 반면 시스템 채팅과 기존 임무 처리는 그대로 유지된다.

## 정책

| 항목 | 정책 |
|---|---|
| 차단 위치 | 채팅방 안에서 상대방을 차단할 수 있다 |
| 차단 가능 시점 | 임무 진행 여부와 관계없이 언제든지 가능하다 |
| 차단 시 일반 채팅 | 한쪽이 차단하면 양쪽 모두 전송할 수 없다 |
| 차단 시 시스템 채팅 | 차단 여부와 관계없이 정상적으로 생성하고 전달한다 |
| 기존 채팅 기록 | 차단 이후에도 양쪽 모두 조회할 수 있다 |
| 새로운 지원 | 한쪽이라도 차단했다면 서로의 요청에 지원할 수 없다 |
| 기존 지원·임무 | 차단해도 자동으로 취소하지 않는다 |
| 임무 완료·분쟁·정산 | 차단 여부와 관계없이 기존 정책대로 처리한다 |
| 차단 해제 | 차단한 사용자만 해제할 수 있다 |
| 차단 해제 후 채팅 | 양쪽 모두 차단하지 않은 상태이고 채팅방이 `ACTIVE`이면 채팅을 다시 보낼 수 있다 |
| 채팅방 상태 | 차단하거나 해제해도 `ACTIVE` / `INACTIVE` / `CLOSED` 상태는 바꾸지 않는다 |

- 차단은 방향이 있다. A가 B를 차단한 것과 B가 A를 차단한 것은 따로 기록하며, 각자 자신이 한 차단만 해제할 수 있다. 둘 다 차단했다면 둘 다 해제해야 채팅을 다시 보낼 수 있다.
- "서로의 요청에 지원할 수 없다"는 양방향이다. A는 B의 요청에, B는 A의 요청에 지원할 수 없다.
- 대기 중인 지원은 두 사람 중 한쪽이라도 차단했다면 매칭할 수 없다. 차단이 있으면 새로 지원할 수 없으므로, 실제로는 지원한 뒤에 차단이 생긴 아래 두 경우다.
  - 꼬붕이 지원한 뒤 그 꼬붕이 행님을 차단한 경우
  - 꼬붕이 지원한 뒤 행님이 그 꼬붕을 차단한 경우
- 매칭할 수 없게 된 지원은 자동 취소 없이 요청이 끝날 때까지 대기 상태로 남는다. 정리가 필요하면 행님은 요청을 취소하고 꼬붕은 지원을 취소할 수 있다. 이미 매칭된 임무는 차단해도 그대로 진행한다.
- 차단해도 채팅방, 요청, 지원은 어느 목록에서도 숨기지 않는다. 차단한 상대의 요청도 홈 목록에 보이며, 지원하려고 하면 거부된다.
- 요청 목록·상세 응답에는 차단 여부를 담지 않는다. 앱은 지원 버튼을 평소처럼 보여주고, 서버가 지원 요청을 받았을 때 거부한다.
- 지원 거부 문구는 누가 차단했는지 드러내지 않는다. 상대가 나를 차단한 사실을 알 수 없게 하기 위해서다. 문구는 [`error-copy-policy.md`](./error-copy-policy.md)에 정한다.
