# 에러 문구 정책 (Error Copy Policy)

> 마지막 업데이트: 2026-08-20
>
> 이 문서는 사용자에게 노출되는 에러 문구의 기획 정본이다. 에러 코드·HTTP 상태·클라이언트 처리 규칙 등
> API 계약은 [`../api-spec/error-codes.md`](../api-spec/error-codes.md)를 우선한다.
> 문구가 스펙과 다르거나 손봐야 할 항목은 [문구 검토 필요](#문구-검토-필요)에 따로 정리한다.

## 책임 경계

| 문서 | 다루는 것 |
|---|---|
| 이 문서 | 사용자에게 보이는 **문구**와 어떤 상황에서 나오는지 |
| [`../api-spec/error-codes.md`](../api-spec/error-codes.md) | 에러 **코드** 목록, HTTP 상태, 클라이언트 분기 규칙 |
| `app/core/errors.py` | 구현 정본. 코드와 문구가 한 곳에 정의돼 있다 |

문구를 바꾸려면 코드 이름을 지정해 요청한다. 코드 이름은 개발용 식별자이며 화면에 노출되지 않는다.

## 도메인 용어

에러 문구는 [알림 정책](./notification-policy.md#도메인-용어-매핑)의 용어 매핑을 따른다. 에러 문구와 알림 문구의 표기는 아래와 같다.

| 내부 코드 용어 | 에러 문구 표기 | 알림 문구 표기 |
|---|---|---|
| Proposal | 요청 | 요청. 홈에 공개되어 지원할 수 있는 요청은 게시물 |
| Offer | 지원 | 지원 |
| Mission | 임무 | 임무 |

에러 문구에서 `제안`·`의뢰` 표기는 쓰지 않는다. 2026-08-20 작업으로 코드베이스에서 제거했다.
Proposal 표기가 알림과 어긋나는 문제는 [문구 검토 필요](#문구-검토-필요)에 기록했다.

## 문구 작성 원칙

- 존댓말 `~습니다`로 끝내고 마침표를 찍는다. 알림 문구의 `~어요` 체와 구분한다.
- 사용자가 고칠 수 있는 상황이면 **무엇을 하면 되는지** 함께 적는다.
  (예: `인증번호가 만료되었습니다. 다시 요청해주세요.`)
- 사용자가 고칠 수 없는 상황이면 원인을 설명하지 않고 재시도만 안내한다.
- 개발 용어(필드명, 영문 상태값, 시스템 이름)를 노출하지 않는다.
- 사용자를 탓하는 표현을 쓰지 않는다.

## 상황별 문구

총 38개 코드를 (사용자 노출 37개 + 방어용 `HTTP_ERROR` 1개) 화면·기능 단위로 묶었다.
`INVALID_TOKEN`처럼 한 코드에 문구가 여러 개인 항목은 문구별로 행을 나눴다. 코드 전체 목록과 HTTP 상태는 [`../api-spec/error-codes.md`](../api-spec/error-codes.md)에 있다.

### 가입 · 로그인

| 에러 코드 | 사용자에게 보이는 문구 | 어떤 상황인가 |
| --- | --- | --- |
| `PHONE_ALREADY_EXISTS` | 이미 가입된 휴대폰 번호입니다. | 가입하려는 번호로 이미 계정이 있을 때. 로그인으로 안내한다. |
| `PHONE_VERIFICATION_NOT_FOUND` | 인증 요청 내역을 찾을 수 없습니다. | 인증번호를 발송한 적 없는 번호로 인증 확인을 시도했을 때. |
| `PHONE_VERIFICATION_CODE_MISMATCH` | 인증번호가 일치하지 않습니다. | 인증번호를 잘못 입력했을 때. |
| `PHONE_VERIFICATION_EXPIRED` | 인증번호가 만료되었습니다. 다시 요청해주세요. | 인증번호를 받은 뒤 제한 시간이 지나 입력했을 때. 재발송이 필요하다. |
| `PHONE_VERIFICATION_SEND_RATE_LIMITED` | 인증번호 요청이 너무 많습니다. 잠시 후 다시 시도해주세요. | 인증번호를 5분 동안 3번 넘게 요청했을 때. 잠시 뒤 다시 시도해야 한다. |
| `USER_NOT_FOUND` | 가입되지 않은 휴대폰 번호입니다. 회원가입 후 이용해주세요. | 가입된 적 없는 번호로 로그인 인증번호를 요청했을 때. 회원가입으로 안내한다. |

## 문구 검토 필요

기획 판단이 필요하거나 손봐야 할 항목이다. 정하면 `app/core/errors.py` 한 줄 수정으로 반영된다.

| 항목 | 현재 | 문제 |
|---|---|---|
| `INVALID_DATE_TIME_FORMAT` | deadline 형식이 올바르지 않습니다. | 개발 필드명 `deadline`이 사용자에게 노출된다. "마감 시각 형식이 올바르지 않습니다." 등으로 교체 필요 |
| `INVALID_TOKEN` | 유효하지 않은 토큰입니다. 외 4종 | 한 코드에 문구가 5종이다. 대부분 앱이 자동 처리해 노출되지 않지만, 노출 화면이 있다면 하나로 통일할지 판단 필요 |
| `USER_WITHDRAWAL_BLOCKED*` | 차단 사유별 문구 5종 + 기본 문구 1종 | 모두 두 문장이라 토스트에 길다. 다이얼로그로 쓸지 문구를 줄일지 결정 필요 |
| SMS 발송 실패 안내 | 문구 없음 | 인증번호 발송이 실패해도 사용자는 정상 응답을 받는다(발송이 응답 이후 비동기로 일어남). 실패를 사용자에게 알릴지, 알린다면 발송을 동기로 바꿀지 기획 판단 필요 |
| Proposal 표기 | 에러는 `요청`, 알림은 `게시물`·`요청` 혼용 | 같은 대상을 화면마다 다르게 부른다. 전 서비스 표기를 하나로 정할지 판단 필요 |

`USER_WITHDRAWAL_BLOCKED` 문구의 `임무` 표기는 2026-08-27 탈퇴 정책 개편에서 `요청`·`지원`으로 교체해 해소했다.

## 문구 변경 절차

1. 이 문서에서 대상 코드 이름과 새 문구를 확정한다.
2. `app/core/errors.py`의 해당 `ApiErrorSpec` 메시지를 수정한다.
3. Swagger 실패 응답 예시는 카탈로그에서 자동 생성되므로 별도 수정이 없다.
4. 문구를 단언하는 테스트가 있으면 함께 갱신한다 (`tests/test_errors.py`, `tests/test_openapi.py`).
5. 이 문서와 [`../api-spec/error-codes.md`](../api-spec/error-codes.md)의 표를 갱신한다.

문구만 바뀌는 변경은 클라이언트 수정이 필요 없다. 클라이언트는 코드로만 분기하고 문구는 그대로 표시한다.
