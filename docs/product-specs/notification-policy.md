# 알림 정책 (Notification Policy)

> 마지막 업데이트: 2026-08-27
>
> 이 문서의 알림 트리거·문구·랜딩 페이지 정본은 기획 내부 스펙이다. 구현 상태 표기는 서버 기준이며,
> 문구가 스펙과 다른 항목은 [문구 불일치](#문구-불일치-스펙-기준-수정-필요)에 따로 정리한다.

## 도메인 용어 매핑

| 내부 코드 용어 | 사용자 표시 용어 |
|---|---|
| Proposal (요청) | 게시물 |
| Offer (지원) | 지원 |
| Orderer (오더러) | 행님 |
| Runner (러너) | 꼬붕 |
| complete_delivery | 꼬붕 만남 확인 ("만났어요") |
| confirm_received | 행님 만남 확인 ("만났어요") |

에러 문구의 용어와 노출 상황은 [`error-copy-policy.md`](./error-copy-policy.md)를 정본으로 한다.

사용자 노출 문구의 호칭은 `행님`(요청자)·`꼬붕`(지원자)으로 통일한다. `요청자`·`지원자`·`꼬봉` 표기는 쓰지 않는다.
수행 대가는 `수행비`로 부른다(`웨이팅비` 표기 폐기).

## 저장 및 발송 조건

클라이언트 전달용 FCM payload 계약은 [`../api-spec/notification-fcm-payload.md`](../api-spec/notification-fcm-payload.md)를 기준으로 한다.

모든 도메인 이벤트 알림은 알림 히스토리용 `notifications` 레코드로 저장한다.
수신자의 `alarm_enabled` 값은 레코드 생성 여부가 아니라 푸시 발송 여부를 결정한다.

- `alarm_enabled = true` → `status=PENDING` 저장 후 FCM 발송 대상
- `alarm_enabled = false` → `status=SKIPPED` 저장 후 FCM 미발송

`SKIPPED` 알림은 사용자가 나중에 알림 설정을 켜도 소급 발송하지 않는다. 읽기 전까지 `read_at=null`로 유지되며 알림 목록과 미읽음 카운트에 포함된다.

## 발송 아키텍처: Outbox 패턴 + Event Publisher/Listener

```
[비즈니스 트랜잭션]
  비즈니스 서비스 (OfferService, ProposalService)
      → EventBus.publish(DomainEvent, db)  ← 같은 DB 세션
      → NotificationEventListener
          → Notification INSERT (alarm_enabled=true: PENDING, false: SKIPPED)
    → db.commit()  ← 비즈니스 데이터 + PENDING 알림 함께 커밋

[비동기 발송 - FastAPI BackgroundTask]
  API 응답 후 즉시 실행
  → NotificationWorker.flush_pending(SessionLocal, notification_ids)
    → 이번 이벤트에서 생성된 PENDING 알림 조회 → FCM 발송 → SENT / FAILED 업데이트

[스케줄러 발송 - APScheduler]
  HTTP 요청 컨텍스트가 없으므로 BackgroundTask 대신 outbox를 직접 flush
  → cancel_expired_payment_proposals (1시간 주기)
  → send_pending_payment_reminders (10분 주기)

[배치 재시도 - APScheduler, 5분 주기]
  → NotificationWorker.retry_failed(SessionLocal)
    → FAILED 중 retry_count < 3 조회 → FCM 재발송
    → 성공: SENT / 실패: retry_count + 1
```

### 발송 제한 규칙

- 동일 이벤트 중복 발송 방지 (디바운스 처리, 최소 간격 10초) — ❌ 미구현
- 지원 알림은 동일 게시물 기준 최대 5회/시간 제한, 초과 시 묶음 알림으로 대체 ("새로운 꼬붕 N명이 생겼어요!") — ❌ 미구현
- 만남 확인 리마인드 최대 2회 (1차: 상대 확인 후 2시간 / 2차: 1차 후 6시간), 이후 미확인 시 운영팀 개입 — ❌ 미구현
- 재시도 최대 3회 (`retry_count < 3`) — ✅ 구현
- `SKIPPED` 상태는 발송 및 재시도 대상에서 제외 — ✅ 구현

## 관리자 운영 알림 (Slack)

앱 사용자에게 나가는 FCM 알림과 별개로, **관리자가 직접 처리해야 진행되는 두 지점**을 Slack
Incoming Webhook으로 통보한다. 관리자 계정은 앱 사용자가 아니라 FCM 토큰이 없다.

설계 근거와 채널 선정 비교는
[`../exec-plans/active/2026-08-27-admin-ops-alert.md`](../exec-plans/active/2026-08-27-admin-ops-alert.md)를 정본으로 한다.

### 트리거

| 미션 전이 | 헤드라인 | 관리자가 할 일 | 상태 |
|---|---|---|---|
| → `DISPUTED` | 🚨 분쟁이 접수됐어요 — 판정이 필요합니다 | 관리자 웹에서 완료 또는 실패로 판정 | ✅ |
| → `COMPLETED` | 💰 미션이 완료됐어요 — 수행비 입금이 필요합니다 | 꼬붕 계좌로 이체 후 지급 기록 | ✅ |

- `COMPLETED`에는 **관리자가 분쟁을 완료로 판정해 도달한 경우도 포함한다.** 판정하는 사람과
  입금하는 사람이 같다는 보장이 없고, 판정 시점이 곧 지급 대기의 시작이다
- `FAILED`(환불 대기)와 `PAID`(종료)는 알리지 않는다. 둘 다 관리자 본인의 조작 결과다
- 한쪽만 만남을 확인한 중간 시점에는 알리지 않는다. 미션이 `STARTED`에 머물기 때문이다
- 이미 그 상태인 미션에는 다시 알리지 않는다. 전이 전후 상태를 비교해 실제로 바뀐 경우에만
  이벤트를 발행한다

### 발송 경로

```
MissionService / AdminCommandService (전이 전후 비교)
  → EventBus.publish(MissionDisputedEvent | MissionCompletedEvent, db)
      → admin_alert_listener → AdminAlert 를 db.info 에 적재 (DB 쓰기 없음)
  → db.commit()
  → 라우터의 BackgroundTask → SlackAdminAlertSender → Incoming Webhook
```

HTTP 호출은 트랜잭션 밖에서 한다. 리스너에서 바로 Slack을 부르면 DB 트랜잭션이 외부 네트워크
지연만큼 길어지고, 뒤에 롤백된 트랜잭션에 대해서도 알림이 나간다.

### 사용자 알림과 다른 점

| 항목 | 사용자 알림(FCM) | 관리자 알림(Slack) |
|---|---|---|
| `notifications` 테이블 저장 | 함 | **안 함** |
| 실패 시 재시도 | 5분 주기 배치, 최대 3회 | **없음. `logger.error`만 남긴다** |
| 미설정 시 | FCM 자격증명 경고 후 발송 안 함 | webhook URL 없으면 경고 후 발송 안 함 (기동은 정상) |

관리자 알림을 영속화하지 않는 이유는 **처리 대기열의 정본이 이미 관리자 웹에 있기** 때문이다.
처리할 분쟁은 `DisputeEvidence.status=PENDING` 목록이고, 입금할 미션은 `MissionStatus.COMPLETED`
목록이다. Slack 메시지는 그 목록을 보라는 재촉이므로 한 건을 놓쳐도 일이 사라지지 않는다.

### 메시지 내용

**꼬붕 정산 계좌는 싣지 않는다.** 정산 계좌는 개인정보이고 Slack 채널은 서버 로그보다 접근
범위가 넓으며 검색·보존된다. 관리자 웹에서 확인한다.

```
🚨 분쟁이 접수됐어요 — 판정이 필요합니다
미션 #12 · 요청 #7 «편의점 담배 심부름»
행님 김가희 / 꼬붕 홍길동 · 수행비 15,000원
관리자 웹에서 완료 또는 실패로 판정해주세요.
<https://admin.example/missions/12|분쟁 처리하러 가기>
```

마지막 링크 줄은 `ADMIN_WEB_BASE_URL`이 설정된 경우에만 붙는다.

### 환경변수

| 변수 | 필수 | 의미 |
|---|---|---|
| `ADMIN_ALERT_SLACK_WEBHOOK_URL` | 아니오 | Slack Incoming Webhook URL. 비면 발송을 건너뛴다. URL 자체가 인증 수단이므로 저장소에 두지 않는다 |
| `ADMIN_WEB_BASE_URL` | 아니오 | 메시지에 붙일 관리자 웹 주소. 비면 링크 줄을 뺀다 |

## 저장 필드와 FCM data

Proposal 단위 알림(게시물 등록 완료, 입금 독촉, 입금 취소)은 `related_entity_type="proposal"`, `related_entity_id=<proposal_id>`로 저장하며 `data`에 `proposal_id`만 담는다. 그 외 알림은 미션 시작 알림을 포함해 모두 `related_entity_type="offer"`, `related_entity_id=<offer_id>`로 저장한다. 이 값은 서버 알림 조회/관리용 DB 필드이며 FCM data payload에는 포함하지 않는다.

`notifications.data`에는 JSON 문자열로 `offer_id`, `proposal_id`를 저장한다. `NotificationWorker`가 FCM으로 전달하는 data payload는 다음 JSON 형태다.

```json
{
  "notification_type": "offer_accepted",
  "offer_id": "45",
  "proposal_id": "10"
}
```

| 필드 | 의미 |
|---|---|
| `notification_type` | `NotificationType` 값. 클라이언트의 현재 라우팅 code로 사용할 수 있다. |
| `offer_id` | `notifications.data.offer_id` |
| `proposal_id` | `notifications.data.proposal_id` |

**랜딩 페이지 미지원**: 스펙의 랜딩 페이지 컬럼을 전달할 `navigation_code`, `target_page`, `deep_link` 필드가 아직 없다. 현재 클라이언트는 `notification_type`으로 화면을 추정해야 하며, "홈", "내 활동 - 수행 기록탭" 같은 목적지는 타입만으로 구분되지 않는다. 랜딩 페이지 정책을 실제로 적용하려면 payload 확장이 선행돼야 한다.

### 현재 구현 주의사항

- 이벤트 기반 outbox 발송은 해당 이벤트에서 생성된 `PENDING` 알림 id만 background task에 전달한다. 기존에 남아 있던 다른 `PENDING` 알림은 이 이벤트의 즉시 발송 대상에 섞지 않는다.
- 이벤트 기반 outbox 발송은 클라이언트 payload를 `notification_type`, `offer_id`, `proposal_id`로 제한한다. 커스텀 알림 직접 발송 경로는 별도 경로로 기존 data prefix를 사용할 수 있다.
- 스케줄러 기반 알림은 최대 1시간(스케줄러 주기) 지연될 수 있다.
