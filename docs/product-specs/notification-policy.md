# 알림 정책 (Notification Policy)

> 마지막 업데이트: 2026-11-18
>
> 기존 기획 문구와 2026-11-18 확정한 지원 전후 전달 정책을 반영한다. 구현 상태는 서버 기준이다.
> 변경 기준은 [NOTI-REQ-001](#noti-req-001--지원-전후-전달-정책)이다.

## 도메인 용어 매핑

| 내부 코드 용어 | 사용자 표시 용어 |
|---|---|
| Proposal (요청) | 요청. 홈에 공개되어 지원할 수 있는 요청은 게시물 |
| Offer (지원) | 지원 |
| Orderer | 행님 |
| Runner | 꼬붕 |
| Mission | 임무 |
| complete_delivery | 꼬붕 임무 완료 ("임무 수행 완료" 버튼) |
| confirm_received | 행님 임무 완료 확인 ("임무 수행 완료" 버튼) |

에러 문구의 용어와 노출 상황은 [`error-copy-policy.md`](./error-copy-policy.md)를 정본으로 한다.

사용자 노출 문구와 문서의 호칭은 `행님`(Orderer)·`꼬붕`(Runner)으로 통일한다. `오더러`·`오더`·`러너`·`요청자`·`지원자`·`수행자`·`꼬봉` 표기는 쓰지 않는다.
수행 대가는 `수행비`로 부른다(`웨이팅비` 표기 폐기).

## 저장 및 발송 조건

클라이언트 전달용 FCM payload 계약은 [`../api-spec/notification-fcm-payload.md`](../api-spec/notification-fcm-payload.md)를 기준으로 한다.

지원 전 도메인 이벤트 알림은 알림 히스토리용 `notifications` 레코드로 저장한다. 지원 등록 이후 사건은 시스템 채팅으로만 저장한다(NOTI-REQ-001).
수신자의 `alarm_enabled` 값은 레코드 생성 여부가 아니라 푸시 발송 여부를 결정한다.

- `alarm_enabled = true` → `status=PENDING` 저장 후 FCM 발송 대상
- `alarm_enabled = false` → `status=SKIPPED` 저장 후 FCM 미발송

`SKIPPED` 알림은 사용자가 나중에 알림 설정을 켜도 소급 발송하지 않는다. 읽기 전까지 `read_at=null`로 유지되며 알림 목록과 미읽음 카운트에 포함된다.

## 발송 아키텍처: Outbox 패턴 + Event Publisher/Listener

```
[비즈니스 트랜잭션]
  지원 전 비즈니스 서비스 (ProposalService, AdminCommandService)
      → 입금 안내: EventBus.publish → NotificationEventListener → Notification INSERT
      → 취소·환불: create_before_offer_notice → Notification INSERT
        (같은 DB 세션, alarm_enabled=true: PENDING, false: SKIPPED)
    → db.commit()  ← 비즈니스 데이터 + PENDING 알림 함께 커밋

[비동기 발송 - FastAPI BackgroundTask]
  API 응답 후 즉시 실행
  → NotificationWorker.flush_pending(SessionLocal, notification_ids)
    → 이번 이벤트에서 생성된 PENDING 알림 조회 → FCM 발송 → SENT / FAILED 업데이트

[스케줄러 발송 - APScheduler]
  HTTP 요청 컨텍스트가 없으므로 BackgroundTask 대신 outbox를 직접 flush
  → cancel_expired_payment_proposals (1시간 주기)
  → send_pending_payment_reminders (10분 주기)

[배치 재시도 - APScheduler, 5분 주기]
  → NotificationWorker.retry_failed(SessionLocal)
    → FAILED 중 retry_count < 3 조회 → FCM 재발송
    → 성공: SENT / 실패: retry_count + 1
```

### 발송 제한 규칙

- 동일 이벤트 중복 발송 방지 (디바운스 처리, 최소 간격 10초) — ❌ 미구현
- 지원 알림은 동일 게시물 기준 최대 5회/시간 제한, 초과 시 묶음 알림으로 대체 ("새로운 꼬붕 N명이 생겼어요!") — ❌ 미구현
- 임무 완료 리마인드 최대 2회 (1차: 상대 확인 후 2시간 / 2차: 1차 후 6시간), 이후 미확인 시 운영팀 개입 — ❌ 미구현
- 재시도 최대 3회 (`retry_count < 3`) — ✅ 구현
- `SKIPPED` 상태는 발송 및 재시도 대상에서 제외 — ✅ 구현

## 관리자 운영 알림 (Slack)

앱 사용자에게 나가는 FCM 알림과 별개로, **관리자가 직접 처리해야 진행되는 두 지점**을 Slack
Incoming Webhook으로 통보한다. 관리자 계정은 앱 사용자가 아니라 FCM 토큰이 없다.

설계 근거와 채널 선정 비교는
[`../exec-plans/active/2026-08-27-admin-ops-alert.md`](../exec-plans/active/2026-08-27-admin-ops-alert.md)를 정본으로 한다.

### 트리거

| 임무 전이 | 헤드라인 | 관리자가 할 일 | 상태 |
|---|---|---|---|
| → `DISPUTED` | 🚨 분쟁이 접수됐어요 — 판정이 필요합니다 | 관리자 웹에서 완료 또는 실패로 판정 | ✅ |
| → `COMPLETED` | 💰 임무가 완료됐어요 — 수행비 입금이 필요합니다 | 꼬붕 계좌로 이체 후 지급 기록 | ✅ |

- `COMPLETED`에는 **관리자가 분쟁을 완료로 판정해 도달한 경우도 포함한다.** 판정하는 사람과
  입금하는 사람이 같다는 보장이 없고, 판정 시점이 곧 지급 대기의 시작이다
- `FAILED`(환불 대기)와 `PAID`(종료)는 알리지 않는다. 둘 다 관리자 본인의 조작 결과다
- 한쪽만 임무 완료를 확인한 중간 시점에는 알리지 않는다. 임무가 `STARTED`에 머물기 때문이다
- 이미 그 상태인 임무에는 다시 알리지 않는다. 전이 전후 상태를 비교해 실제로 바뀐 경우에만
  이벤트를 발행한다

### 발송 경로

```
MissionService / AdminCommandService (전이 전후 비교)
  → EventBus.publish(MissionDisputedEvent | MissionCompletedEvent, db)
      → admin_alert_listener → AdminAlert 를 db.info 에 적재 (DB 쓰기 없음)
  → db.commit()
  → 라우터의 BackgroundTask → SlackAdminAlertSender → Incoming Webhook
```

HTTP 호출은 트랜잭션 밖에서 한다. 리스너에서 바로 Slack을 부르면 DB 트랜잭션이 외부 네트워크
지연만큼 길어지고, 뒤에 롤백된 트랜잭션에 대해서도 알림이 나간다.

### 사용자 알림과 다른 점

| 항목 | 사용자 알림(FCM) | 관리자 알림(Slack) |
|---|---|---|
| `notifications` 테이블 저장 | 함 | **안 함** |
| 실패 시 재시도 | 5분 주기 배치, 최대 3회 | **없음. `logger.error`만 남긴다** |
| 미설정 시 | FCM 자격증명 경고 후 발송 안 함 | webhook URL 없으면 경고 후 발송 안 함 (기동은 정상) |

관리자 알림을 영속화하지 않는 이유는 **처리 대기열의 정본이 이미 관리자 웹에 있기** 때문이다.
처리할 분쟁은 `DisputeEvidence.status=PENDING` 목록이고, 입금할 임무는 `MissionStatus.COMPLETED`
목록이다. Slack 메시지는 그 목록을 보라는 재촉이므로 한 건을 놓쳐도 일이 사라지지 않는다.

### 메시지 내용

**꼬붕 정산 계좌는 싣지 않는다.** 정산 계좌는 개인정보이고 Slack 채널은 서버 로그보다 접근
범위가 넓으며 검색·보존된다. 관리자 웹에서 확인한다.

```
🚨 분쟁이 접수됐어요 — 판정이 필요합니다
임무 #12 · 요청 #7 «편의점 담배 심부름»
행님 김가희 / 꼬붕 홍길동 · 수행비 15,000원
관리자 웹에서 완료 또는 실패로 판정해주세요.
<https://admin.example/missions/12|분쟁 처리하러 가기>
```

마지막 링크 줄은 `ADMIN_WEB_BASE_URL`이 설정된 경우에만 붙는다.

### 환경변수

| 변수 | 필수 | 의미 |
|---|---|---|
| `ADMIN_ALERT_SLACK_WEBHOOK_URL` | 아니오 | Slack Incoming Webhook URL. 비면 발송을 건너뛴다. URL 자체가 인증 수단이므로 저장소에 두지 않는다 |
| `ADMIN_WEB_BASE_URL` | 아니오 | 메시지에 붙일 관리자 웹 주소. 비면 링크 줄을 뺀다 |

## NotificationType 매핑과 클릭

| 사건 | 타입 | 클릭 시 |
|---|---|---|
| 게시물 등록 완료 | `PAYMENT_COMPLETED` | 요청 상세 |
| 입금 독촉 | `PAYMENT_REMINDER` | 홈 |
| 미입금 자동 취소 | `PROPOSAL_CANCELLED` | 홈 |
| **지원 전 행님 취소** | **`PROPOSAL_CANCELLED_BY_USER`** | **요청 상세** |
| **지원 전 관리자 취소** | **`PROPOSAL_CANCELLED_BY_ADMIN`** | **요청 상세** |
| **지원 전 환불 완료** | **`REFUND_COMPLETED`** | **요청 상세** |

기존 지원 이후 타입(`OFFER_NEW`, `OFFER_SUBMITTED`, `OFFER_ACCEPTED`, `OFFER_REJECTED`, `PROPOSAL_MATCHED`, `MEETING_CONFIRMED`, `EXECUTION_COMPLETED`, `DISPUTE_RAISED`)은 과거 이력 조회 호환을 위해 남긴다. 이 사건의 새 notifications는 생성하지 않는다.

## 저장 필드와 FCM data

지원 전 알림은 `related_entity_type="proposal"`, `related_entity_id=<proposal_id>`로 저장하고 JSON data에 `proposal_id`를 담는다. FCM data는 타입과 문자열 ID를 전달한다.

```json
{"notification_type": "refund_completed", "proposal_id": "10"}
```

지원 이후는 채팅 outbox를 사용한다. `type=CHAT`, `roomId`, `messageId`, `seq`로 해당 채팅방을 연다. 상세 계약은 [FCM payload](../api-spec/notification-fcm-payload.md)를 따른다. 실제 화면 이동은 클라이언트가 구현한다.

### 현재 구현 주의사항

- 이벤트 기반 outbox 발송은 해당 이벤트에서 생성된 `PENDING` 알림 id만 background task에 전달한다. 기존에 남아 있던 다른 `PENDING` 알림은 이 이벤트의 즉시 발송 대상에 섞지 않는다.
- 이벤트 기반 outbox 발송은 클라이언트 payload를 `notification_type`, `offer_id`, `proposal_id`로 제한한다. 커스텀 알림 직접 발송 경로는 별도 경로로 기존 data prefix를 사용할 수 있다.
- 스케줄러 기반 알림은 최대 1시간(스케줄러 주기) 지연될 수 있다.

## NOTI-REQ-001 — 지원 전후 전달 정책

2026-11-18 확정. 지원 전은 기존 알림, 지원 등록부터는 시스템 채팅을 사용한다. 전체 공지·관리자 커스텀 알림은 이 분류와 무관하며 유지한다. 과거 notifications 이력은 삭제하지 않는다.

- **변경:** 지원 등록·매칭·미선정·완료·분쟁의 기존 알림 저장/발송을 제거하고 시스템 채팅으로 통합한다. 제목·본문은 현재 구현 문구를 공백·이모지까지 그대로 유지한다. 수행비 입금의 꼬붕 문구는 위 정책 문구를 사용한다(OOO는 쉼표 포함 실제 금액).
- 채팅 내용은 수신자별 본문, `systemTitle`은 수신자별 기존 알림 제목(null이면 기존처럼 상대 이름으로 푸시). 일반 채팅의 `systemTitle`은 null이다.
- 시스템 채팅 푸시는 `type=CHAT`, `roomId`, `messageId`, `seq`로 해당 채팅방을 연다. 종료된 방도 조회 가능하다. 기존 알림과 시스템 채팅을 중복 생성하지 않는다.
- 미선정 행님은 기록만 유지(안읽음·푸시 제외). 나머지 기존 시스템 채팅의 안읽음·푸시 대상은 유지하고 기존 알림 수신자도 시스템 푸시 대상에 포함한다. 탈퇴자·알림 꺼짐은 푸시 제외.
- **추가:** 지원 전 행님 취소: 제목 `요청이 취소됐어요.`, 본문 `요청이 취소됐어요.`. 관리자 취소: 제목 `요청이 취소됐어요.`, 본문 `관리자에 의해 요청이 취소됐어요.`. 기존 문구가 없어서 이 문구를 신규 정의한다.
- **추가:** 지원 전 환불 완료: 제목 `환불이 완료됐어요.`, 본문 `행님에게 환불이 완료됐어요.`(기존 시스템 본문 재사용).
- 세 신규 알림은 행님에게 저장하고, 각각 `proposal_cancelled_by_user`, `proposal_cancelled_by_admin`, `refund_completed`와 `proposal_id`로 요청 상세를 연다. 알림 꺼짐은 SKIPPED로 저장한다. 업무 변경과 같은 트랜잭션으로 저장하고 커밋 후 즉시 발송 대상으로 넘긴다.
- **추가:** 지원 후·매칭 전 환불 완료는 해당 요청의 기존 채팅방 모두에 `행님에게 환불이 완료됐어요.`를 한 번씩 기록한다. 닫힌 방도 포함한다. 매칭 후에는 매칭된 방만 기록한다. 지원 여부는 지원 이력(취소 포함)으로 판단하며, 기존 지원은 0037 채팅방 백필이 선행되어야 한다.
- **삭제:** 카카오톡 입장 코드·채팅방 개설·개설 실패 안내. 기존 API/DB 오픈채팅 필드 제거는 TD-020 배포 순서를 따른다.
- **보류:** 요청 만료 안내(지원 전 행님 기존 알림, 지원 후 행님·꼬붕 시스템 채팅)와 자동 만료는 사용자 결정에 따라 TD-021로 미룬다. 꼬붕 신규 문구 초안은 `요청이 만료되어 채팅이 종료됐어요.`이며 후속 구현 때 확정한다.
- 완료 리마인드 1·2차는 기존 미구현 상태를 유지하고, 후속 구현 시 시스템 채팅으로 전달한다. 관리자 게시글 신고 승인 안내는 TD-027로 보류한다.
