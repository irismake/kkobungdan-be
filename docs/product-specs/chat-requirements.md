# 채팅 요구사항

> 상태: 구현됨 (2026-11-18, 사용자 차단 관련 요구사항은 차단 구현 후)
> 관련 문서: [`../domains/chat/test-scenarios.md`](../domains/chat/test-scenarios.md), [`../design-docs/chat-architecture.md`](../design-docs/chat-architecture.md), [`../exec-plans/active/2026-11-14-tdd-harness.md`](../exec-plans/active/2026-11-14-tdd-harness.md), [`user-block.md`](./user-block.md), [`chat-reporting.md`](./chat-reporting.md)

## 목적

지금은 매칭 후 카카오톡 오픈채팅방 입장 코드로 대화한다. 행님과 꼬붕이 앱을 벗어나야 하고, 지원 단계에서는 대화할 방법이 없으며, 대화 기록이 서비스에 남지 않아 분쟁 때 근거로 쓸 수 없다.

앱 안의 채팅으로 이를 대체한다. 꼬붕이 지원하는 순간부터 행님과 1:1로 대화하고, 임무 진행 상황을 시스템 채팅으로 함께 확인하며, 대화 기록은 서비스에 남는다.

## 범위

### 포함

- 카카오톡 오픈채팅방을 앱 내 채팅으로 대체한다. 오픈채팅 제거는 앱 채팅 배포 후 별도 작업으로 한다. ([`TD-020`](../exec-plans/tech-debt-tracker.md))
- 텍스트 채팅, 시스템 채팅, 읽음 처리, 실시간 수신, 채팅 푸시

### 제외

- 사용자 차단 구현은 별도 브랜치에서 한다. 차단 정책(차단 시점, 지원·매칭 제한, 요청·지원 목록 표시)은 [`user-block.md`](./user-block.md)에서 다룬다. 이 문서의 [사용자 차단 상태](#사용자-차단-상태)는 차단이 채팅에 주는 영향만 다룬다.
- 채팅 신고는 [`chat-reporting.md`](./chat-reporting.md)에서 다룬다.
- 사진·파일 전송은 이번 범위에서 제외하고 후속 작업으로 한다. 채팅은 텍스트만 보낼 수 있다.
- 채팅방 나가기·삭제는 제공하지 않는다. 채팅방은 임무 기록과 분쟁 근거이므로 항상 목록에 남는다.
- 채팅 내용의 전화번호·계좌번호를 막거나 경고하지 않는다. 만남 장소 조율 등에 연락처가 필요할 수 있다.
- 채팅 기록의 보관 기한은 이번에 정하지 않는다. 지금은 삭제하지 않으며, 개인정보 처리방침에 맞춘 보관 기간은 후속 작업으로 정한다.

## 사용자와 권한

| 역할 | 할 수 있는 일 | 할 수 없는 일 |
|------|---------------|---------------|
| 행님 | 자신의 요청에 지원한 모든 꼬붕의 채팅방 조회, 채팅 전송(`ACTIVE`이고 차단이 없을 때), 읽음 처리, 상대방 차단·신고 | 다른 사람 요청의 채팅방 조회, 시스템 채팅 생성·수정, 채팅방 나가기·삭제 |
| 꼬붕 | 자신이 지원한 요청의 채팅방 조회, 채팅 전송(`ACTIVE`이고 차단이 없을 때), 읽음 처리, 상대방 차단·신고 | 다른 꼬붕의 채팅방 조회, 시스템 채팅 생성·수정, 채팅방 나가기·삭제 |
| 관리자 | 관리자 웹에서 모든 채팅방의 채팅 조회, 채팅 신고 처리 | 채팅 전송, 참여자의 읽음 상태 변경 |

- 채팅방 참여자가 아닌 제3자는 채팅방에 접근할 수 없다 (CHAT-REQ-002).
- 같은 사용자가 어떤 요청에서는 행님, 다른 요청에서는 꼬붕일 수 있다. 권한은 채팅방마다 그 채팅방에서의 역할로 판단한다.

## 채팅방 상태

채팅을 보낼 수 있는지를 표현한다. 임무가 어떤 단계에 있는지는 요청·지원 상태가 표현하므로 채팅방은 이를 중복해서 갖지 않는다.

| 상태 | 의미 | 채팅 전송 | 다시 활성화 |
|------|------|-------------|-------------|
| `ACTIVE` | 채팅을 주고받을 수 있는 상태 | 가능 | — |
| `INACTIVE` | 일시적으로 채팅을 보낼 수 없는 상태. 이후 `ACTIVE` 또는 `CLOSED`가 될 수 있다 | 불가 | 가능 |
| `CLOSED` | 채팅이 끝난 상태 | 불가 | 불가 |

- 채팅방 상태는 임무 변화로만 바뀐다. `INACTIVE`가 되는 경우는 현재 분쟁 접수뿐이며, 분쟁 판정이 나면 `CLOSED`가 된다. `INACTIVE`에서 `ACTIVE`로 돌아가는 경우는 아직 없고 확장을 위해 둔다.
- 사용자 차단은 채팅방 상태에 반영하지 않고 [사용자 차단 상태](#사용자-차단-상태)로 따로 관리한다. 두 정보는 서로 바꾸지 않는다.
- 채팅은 채팅방이 `ACTIVE`이고 차단이 없을 때만 보낼 수 있다. 서버는 이 조건으로 전송을 거부한다. 전송 가능 여부를 합친 별도 필드는 두지 않으며, 앱은 채팅방 상태와 차단 여부를 함께 보고 판단한다.
- 채팅방 상태는 채팅 전송만 제어한다. 지원 취소, 매칭, 임무 완료, 분쟁 접수 같은 임무 동작은 채팅방 상태와 관계없이 요청·지원 상태로 허용 여부를 판단한다. 예를 들어 상대를 차단한 상태에서도 임무 완료를 확인할 수 있다. 차단이 지원·매칭에 주는 영향은 [`user-block.md`](./user-block.md)를 따른다.
- 앱의 상태 배지와 채팅방 안의 버튼(지원 취소, 매칭, 임무 완료)은 채팅방 상태가 아니라 요청·지원 상태로 표시한다. 채팅방 응답에 요청·지원 상태를 함께 담는다.

### 상태 이유 (`statusReason`)

같은 상태라도 앱에 보여줄 내용이 다르면 상태를 늘리지 않고 `statusReason`으로 구분한다.

| 상태 | statusReason | 경우 |
|------|--------------|------|
| `ACTIVE` | `null` | 지원 등록 후 매칭 대기, 매칭 후 임무 진행 중 |
| `INACTIVE` | `ORDERER_DISPUTED` | 행님이 분쟁을 접수함 |
| `INACTIVE` | `RUNNER_DISPUTED` | 꼬붕이 분쟁을 접수함 |
| `CLOSED` | `NOT_SELECTED` | 행님이 다른 꼬붕을 매칭함 |
| `CLOSED` | `OFFER_CANCELLED` | 꼬붕이 지원을 취소함 |
| `CLOSED` | `OFFER_CANCELLED` | 꼬붕이 회원 탈퇴하여 대기 중인 지원이 자동 취소됨 |
| `CLOSED` | `PROPOSAL_CANCELLED` | 행님이 매칭 전에 요청을 취소함 |
| `CLOSED` | `ADMIN_CANCELLED` | 관리자가 매칭 전에 요청을 취소함 |
| `CLOSED` | `ADMIN_CANCELLED` | 관리자가 게시글 신고를 승인함 (요청 `REPORTED`) |
| `CLOSED` | `ADMIN_CANCELLED` | 관리자가 매칭 후 요청을 취소함 |
| `CLOSED` | `ALL_CONFIRMED` | 행님과 꼬붕이 모두 임무 완료를 확인함 |
| `CLOSED` | `DISPUTE_COMPLETED` | 분쟁 판정 결과 행님 책임 (임무 `COMPLETED`) |
| `CLOSED` | `DISPUTE_FAILED` | 분쟁 판정 결과 꼬붕 책임 (임무 `FAILED`) |

- 임무 진행 상황(한쪽만 완료 확인 등)은 채팅방 이유로 표현하지 않는다. 지원 상태와 완료 확인 시각으로 알 수 있다.
- 환불 대기·완료는 채팅방 이유로 표현하지 않는다. 요청 상태(`REFUND_PENDING`, `REFUNDED`) 배지로 보여준다.
- 탈퇴한 상대의 이름은 기존 앱 응답과 같이 `"탈퇴한 사용자"`로 내려준다. 탈퇴는 `statusReason`으로 구분하지 않는다.

## 사용자 차단 상태

해당 사용자가 상대방을 차단했는지를 사용자 사이의 관계로 기록한다. 채팅방 상태와 별도로 관리하며 채팅방 상태를 바꾸지 않는다.

| 상태 |
|------|
| 차단하지 않음 |
| 차단함 |

- 차단은 채팅방 단위가 아니라 사용자 단위다. 차단하면 그 사용자와의 모든 채팅방에서 채팅을 보낼 수 없다.
- 한쪽이 차단하면 양쪽 모두 채팅을 보낼 수 없다.
- 차단해도 채팅방은 목록에서 숨기지 않는다. 기존 채팅과 안읽음 수는 그대로 남는다.
- 차단 중에는 서버가 만드는 시스템 채팅만 채팅방에 새로 저장된다. 매칭, 분쟁 접수처럼 임무 진행에 따라 생기는 시스템 채팅은 양쪽 모두에게 보이며 안읽음 수에 포함한다.
- 차단은 차단한 사람만 해제할 수 있다. 해제하면 차단 기록만 바뀌고 채팅방 상태는 바뀌지 않는다.
- 채팅방 응답에는 차단 여부(차단 안 함 / 내가 차단함 / 상대가 차단함)를 함께 담는다.

## 기능 요구사항

카테고리는 요구사항 분류용이며 작업 단위가 아니다.

### 1. 채팅방 생성 및 참여 권한

#### CHAT-REQ-001 — 채팅방 생성

- **Who:** 꼬붕
- **When:** 행님의 요청(Proposal)에 꼬붕이 지원(Offer)을 정상 등록했을 때
- **What:**
  - Offer 1건당 채팅방 1개를 자동 생성한다.
  - 채팅방은 해당 요청의 행님과 지원한 꼬붕, 총 2명으로 구성된다.
  - 하나의 요청에 여러 꼬붕이 지원했다면 꼬붕별로 독립적인 채팅방을 생성한다.
  - 동일한 꼬붕은 하나의 요청에 한 번만 지원할 수 있으므로, 동일한 행님과 꼬붕 사이에 같은 요청에 대한 채팅방은 1개만 생성된다.
  - 지원 취소 후 같은 요청에 다시 지원할 수 없으므로, 같은 요청에 대한 채팅방도 다시 생성되지 않는다.
  - 동일한 두 명의 사용자라도 서로 다른 요청에 대한 지원이라면 각각 별도의 채팅방을 생성할 수 있다.
  - 채팅방 생성 시 초기 상태는 `ACTIVE`이다.

#### CHAT-REQ-002 — 채팅방 접근 권한

- **Who:** 행님, 꼬붕
- **When:** 채팅방에 접근하거나 채팅 목록을 조회할 때
- **What:**
  - 행님은 자신이 등록한 요청에 지원한 모든 꼬붕의 채팅방에 접근할 수 있다.
  - 꼬붕은 자신이 지원한 요청의 채팅방에만 접근할 수 있다.
  - 채팅방 참여자가 아닌 제3자는 접근할 수 없다. 기존 API와 같이 `403 FORBIDDEN`을 반환한다.
  - 채팅방이 종료되거나 상대방을 차단한 이후에도 기존 참여자의 채팅방 조회 권한은 유지된다.
  - 관리자는 관리자 웹에서 모든 채팅방의 채팅 내용을 조회할 수 있다. 관리자는 채팅을 전송할 수 없고, 관리자의 조회는 참여자의 읽음 상태를 바꾸지 않는다.

### 2. 채팅 전송 및 조회

#### CHAT-REQ-003 — 채팅 전송

- **Who:** 행님, 꼬붕
- **When:** 채팅방이 `ACTIVE` 상태일 때
- **What:**
  - 채팅방 참여자는 텍스트 채팅을 전송할 수 있다.
  - 전송된 채팅은 서버에 저장한다.
  - 채팅에는 발신자, 내용, 전송 시각을 기록한다.
  - 채팅은 해당 채팅방의 행님과 꼬붕만 주고받을 수 있다.
  - 일반 채팅은 최대 500자까지 입력할 수 있다.
  - 공백·줄바꿈만 있는 채팅은 전송할 수 없다.
  - 글자 수는 화면에 보이는 글자 단위(grapheme cluster)로 센다. 앱(Swift `String.count`)과 같은 기준이며, 첫 인사(CHAT-REQ-006)에도 같은 기준을 적용한다.
  - 전송 시각은 기존 API와 같이 UTC로 응답한다.

#### CHAT-REQ-004 — 채팅 조회

- **Who:** 행님, 꼬붕
- **When:** 자신이 참여한 채팅방에 접근했을 때
- **What:**
  - 해당 채팅방에 저장된 채팅 내역을 조회할 수 있다.
  - 채팅은 전송된 순서대로 조회할 수 있다.
  - 채팅방에 들어가면 최근 채팅 30개를 먼저 조회하고, 이전 채팅은 30개씩 추가로 조회할 수 있다.
  - 각 채팅의 발신자, 내용, 전송 시각을 확인할 수 있다.

#### CHAT-REQ-014 — 채팅 목록 조회

- **Who:** 행님, 꼬붕
- **When:** 채팅 목록 화면을 볼 때
- **What:**
  - 역할과 관계없이 자신이 참여한 모든 채팅방을 목록으로 조회할 수 있다. `ACTIVE`, `INACTIVE`, `CLOSED` 상태의 채팅방과 차단한 상대의 채팅방도 포함한다.
  - 목록은 마지막 채팅 시각이 최신인 채팅방부터 보여준다. 채팅이 없는 채팅방은 채팅방 생성 시각을 기준으로 한다.
  - 각 채팅방에는 상대방 이름, 요청 제목, 마지막 채팅 내용, 마지막 채팅 시각, 안읽음 수(CHAT-REQ-011)를 보여준다. 같은 두 사용자 사이에 요청별로 채팅방이 여러 개일 수 있으므로 요청 제목으로 구분한다.
  - 마지막 채팅이 시스템 채팅이면 그 내용을 마지막 채팅으로 보여준다.
  - 각 채팅방에는 채팅방 상태, `statusReason`, 요청·지원 상태, 차단 여부를 함께 담는다.
  - 탈퇴한 상대의 이름은 `"탈퇴한 사용자"`로 내려준다.
  - 이전 채팅방 목록을 추가로 조회할 수 있다.
  - 새 채팅이 오면 해당 채팅방의 마지막 채팅, 안읽음 수, 순서가 갱신된다.
  - 채팅 목록을 조회하는 것만으로는 읽음 처리하지 않는다 (CHAT-REQ-010).

#### CHAT-REQ-005 — 채팅 기록 유지

- **Who:** 행님, 꼬붕
- **When:** 채팅방 상태가 변경되거나, 상대방을 차단했거나, 상대방이 회원 탈퇴했을 때
- **What:**
  - 채팅방이 `INACTIVE` 또는 `CLOSED` 상태로 변경되어도 기존 채팅 기록을 유지한다.
  - 상대방이 회원 탈퇴해도 그 사람이 보낸 채팅 내용은 지우거나 가리지 않는다. 발신자 이름만 `"탈퇴한 사용자"`로 보여준다.
  - 상대방을 차단하거나 차단당하더라도 기존 채팅 기록을 조회할 수 있다.
  - 채팅 전송이 제한된 상태에서도 기존 채팅 기록은 조회할 수 있다.

#### CHAT-REQ-006 — 지원 시 첫 인사 채팅

- **Who:** 꼬붕
- **When:** 행님의 요청(Proposal)에 지원(Offer)을 등록했을 때
- **What:**
  - 꼬붕이 지원 시 작성한 첫 인사를 해당 채팅방에 자동 저장한다.
  - 첫 인사는 꼬붕이 전송한 일반 채팅으로 저장한다.
  - 첫 인사는 필수 입력이다. 공백·줄바꿈만 있으면 입력하지 않은 것으로 본다.
  - 첫 인사는 최대 500자까지 입력할 수 있다. 글자 수 기준은 CHAT-REQ-003과 같다.
  - 지원 등록과 첫 인사 저장은 함께 성공하거나 실패해야 한다.

### 3. 요청 상태에 따른 채팅 제어

#### CHAT-REQ-007 — 채팅방 상태 변경

- **Who:** 서버
- **When:** 요청(Proposal) 또는 지원(Offer)의 상태가 변경되었을 때
- **What:**
  - 지원 등록 시 채팅방을 `ACTIVE` 상태로 생성한다.
  - 행님이 꼬붕을 선택하여 매칭하면 해당 채팅방은 `ACTIVE`를 유지한다.
  - 매칭되지 않은 다른 꼬붕의 채팅방은 `CLOSED`로 변경한다.
  - 꼬붕이 지원을 취소하거나 행님이 요청을 취소하면 해당 채팅방을 `CLOSED`로 변경한다.
  - 관리자가 요청을 취소하면 `CLOSED`가 아닌 채팅방을 `CLOSED`로 변경한다. 단, 분쟁 중인 요청은 관리자 취소 대상에서 제외한다.
  - 관리자가 게시글 신고를 승인하여 요청이 `REPORTED` 상태가 되면, 거절 처리된 대기 지원의 채팅방을 `CLOSED`로 변경한다.
  - 꼬붕이 회원 탈퇴하여 대기 중인 지원이 자동 취소되면 해당 채팅방을 `CLOSED`로 변경한다.
  - 행님과 꼬붕이 모두 임무 완료를 확인하면 `CLOSED`로 변경한다.
  - 분쟁이 접수되면 해당 채팅방을 `INACTIVE`로 변경한다.
  - 관리자가 분쟁을 판정하면 `INACTIVE` 상태를 `CLOSED`로 변경한다.
  - 상태와 함께 바뀌는 `statusReason`은 [상태 이유](#상태-이유-statusreason) 표를 따른다.

#### CHAT-REQ-008 — 임무 완료 처리

- **Who:** 행님, 꼬붕
- **When:** 매칭되어 임무가 진행 중일 때 (지원 `ACCEPTED` 또는 `RUNNER_COMPLETED`)
- **What:**
  - 행님과 꼬붕은 각각 임무 완료를 확인할 수 있다. 채팅방 상태나 차단 여부와 관계없이 가능하다.
  - 한쪽만 완료를 확인한 경우 채팅방 상태는 바뀌지 않는다.
  - 양쪽 모두 완료를 확인하면 채팅방을 `CLOSED`로 변경한다.
  - 이미 완료를 확인한 사용자는 중복으로 완료 처리할 수 없다. 다시 확인을 요청하면 오류로 거부하고 채팅방 상태와 시스템 채팅은 바꾸지 않는다.

#### CHAT-REQ-009 — 채팅 전송 제한

- **Who:** 행님, 꼬붕
- **When:** 채팅방이 `INACTIVE` 또는 `CLOSED` 상태일 때
- **What:**
  - 새로운 채팅을 전송할 수 없다.
  - 채팅방 상태가 변경된 이후에는 이전 상태를 기준으로 새로운 채팅을 저장할 수 없다.
  - 채팅 전송이 제한되어도 기존 채팅 내역은 조회할 수 있다.
  - 사용자 차단에 따른 채팅 전송 제한은 [사용자 차단 상태](#사용자-차단-상태) 규칙을 따른다.

### 4. 읽음 처리

#### CHAT-REQ-010 — 채팅 읽음 처리

- **Who:** 행님, 꼬붕
- **When:** 자신이 참여한 채팅방에 들어갔거나, 채팅방을 보고 있는 중에 새 채팅을 받았거나, 채팅을 전송했을 때
- **What:**
  - 채팅방 참여자별로 읽음 상태를 독립적으로 관리한다. 읽음 상태는 참여자가 마지막으로 읽은 채팅으로 기록한다.
  - 채팅방에 들어가면 그 시점까지 채팅방에 저장된 모든 채팅을 읽음 처리한다.
  - 채팅방을 보고 있는 동안 새로 받은 채팅도 읽음 처리한다.
  - 채팅을 전송하면 그 채팅보다 먼저 저장된 채팅까지 읽음 처리한다. 앱의 읽음 요청이 실패했더라도 답장을 보내면 읽음 상태가 맞춰진다.
  - 채팅 목록에서 채팅방의 마지막 채팅 미리보기를 보는 것만으로는 읽음 처리하지 않는다.
  - 읽음 위치는 뒤로만 이동한다. 이미 읽은 위치와 같거나 그보다 앞선 채팅으로 요청하면 오류 없이 성공으로 응답하고 읽음 상태를 유지한다. 늦게 도착한 이전 읽음 요청도 같다.
  - 해당 채팅방에 없는 채팅으로 읽음 처리를 요청하면 거부한다.
  - 채팅방 상태(`ACTIVE`, `INACTIVE`, `CLOSED`)나 차단 여부와 관계없이 읽음 처리할 수 있다.
  - 관리자의 조회는 참여자의 읽음 상태를 바꾸지 않는다 (CHAT-REQ-002).

#### CHAT-REQ-011 — 안읽음 채팅 수

- **Who:** 행님, 꼬붕
- **When:** 새로운 채팅을 받거나 채팅을 읽음 처리했을 때
- **What:**
  - 채팅방별 안읽음 수는 마지막으로 읽은 채팅 이후에 저장된 채팅 중 상대방이 보낸 일반 채팅과 시스템 채팅의 수다.
  - 자신이 보낸 일반 채팅은 안읽음 수에 포함하지 않는다.
  - 꼬붕이 지원 시 작성한 첫 인사(CHAT-REQ-006)는 일반 채팅이므로 행님의 안읽음 수에 포함한다.
  - 시스템 채팅은 그 채팅을 볼 수 있는 참여자의 안읽음 수에 포함한다. 푸시를 보내지 않는 시스템 채팅도 안읽음 수에 포함한다. 단, CHAT-REQ-021 표에서 안읽음 제외로 정한 경우(매칭 미선정 안내의 행님)는 포함하지 않는다.
  - 채팅방별 안읽음 수와 전체 채팅방의 안읽음 합계를 제공한다. 전체 합계는 앱 아이콘 배지 숫자 계산에 사용한다 (CHAT-REQ-018).
  - 채팅방이 종료되거나 상대방을 차단해도 읽지 않은 채팅의 안읽음 수는 유지하며 전체 합계에 포함한다.

#### CHAT-REQ-012 — 전체 읽음 처리

- **Who:** 행님, 꼬붕
- **When:** 사용자가 전체 채팅 읽음 처리를 요청했을 때
- **What:**
  - 역할과 관계없이 자신이 참여한 모든 채팅방에서, 요청을 받은 시점까지 저장된 채팅을 읽음 처리한다.
  - 요청을 받은 이후에 저장된 채팅은 읽음 처리하지 않는다.
  - 이미 그 시점보다 뒤의 채팅까지 읽은 채팅방은 읽음 상태를 유지한다 (CHAT-REQ-010).
  - 다른 사용자의 읽음 상태에는 영향을 주지 않는다.
  - `ACTIVE`, `INACTIVE`, `CLOSED` 상태의 채팅방과 차단한 상대의 채팅방 모두 대상에 포함한다.

#### CHAT-REQ-013 — 상대방 읽음 표시

- **Who:** 행님, 꼬붕
- **When:** 채팅방에서 자신이 보낸 채팅을 볼 때
- **What:**
  - 자신이 보낸 채팅 중 상대방이 아직 읽지 않은 채팅에 안읽음 표시(`1`)를 보여준다.
  - 상대방이 읽으면 표시가 사라진다. 채팅방을 보고 있는 중에 상대방이 읽으면 실시간으로 사라진다.
  - 채팅방 응답에 상대방이 마지막으로 읽은 채팅을 담는다.
  - 시스템 채팅에는 안읽음 표시를 하지 않는다.

### 5. 실시간 채팅 수신 및 재연결

#### CHAT-REQ-015 — 실시간 채팅 수신

- **Who:** 행님, 꼬붕
- **When:** 자신이 참여한 채팅방에 새로운 채팅이 저장되었을 때
- **What:**
  - 실시간 연결은 채팅방 단위가 아니라 사용자 단위다. 연결된 사용자는 역할과 관계없이 자신이 참여한 모든 채팅방의 새 채팅을 받는다. 채팅 목록(CHAT-REQ-014)과 안읽음 합계(CHAT-REQ-011)도 이 연결로 갱신한다.
  - 일반 채팅과 시스템 채팅 모두 실시간으로 전달한다.
  - 서버는 저장에 성공한 채팅만 전달한다. 실시간 전달에 실패해도 저장된 채팅은 유지되며 다시 조회할 수 있다.
  - 채팅방 참여자가 아닌 제3자에게는 전달하지 않는다.
  - 같은 채팅이 여러 번 전달될 수 있다. 앱은 채팅 ID로 같은 채팅을 한 번만 보여준다.
  - 앱은 전달받은 순서가 아니라 서버에 저장된 순서대로 채팅을 보여준다.
  - 채팅방을 보고 있는 중에 받은 채팅은 읽음 처리한다 (CHAT-REQ-010).

#### CHAT-REQ-016 — 연결 끊김 및 재연결

- **Who:** 행님, 꼬붕
- **When:** 네트워크 장애, 앱 백그라운드 전환 등으로 실시간 연결이 끊겼다가 복구되었을 때
- **What:**
  - 연결이 끊긴 동안 저장된 채팅도 서버에 그대로 유지한다.
  - 연결이 복구되면 실시간 수신을 다시 시작한다.
  - 앱은 채팅방별로 마지막으로 받은 채팅 이후의 채팅을 저장 순서대로 조회하여 놓친 채팅을 복구할 수 있다. 이 기준으로 조회하면 중복되거나 빠지는 채팅이 없다.
  - 재연결 시 채팅 목록, 안읽음 수, 상대방의 읽음 위치도 최신 상태로 다시 받을 수 있다.
  - 재연결 시 사용자의 인증과 채팅방 참여 권한을 다시 확인한다. access token이 만료되었으면 연결을 거부하고, 앱은 토큰을 갱신한 뒤 다시 연결한다.
  - 연결된 동안 access token이 만료되면 서버는 연결을 끊는다. 앱은 토큰을 갱신한 뒤 다시 연결한다.
  - 채팅방이 `INACTIVE` 또는 `CLOSED` 상태여도 놓친 채팅을 복구할 수 있다.

#### CHAT-REQ-017 — 채팅방 상태 변경 실시간 반영

- **Who:** 행님, 꼬붕
- **When:** 참여 중인 채팅방의 상태, 요청·지원 상태, 읽음 상태, 차단 상태가 바뀌었을 때
- **What:**
  - 채팅방 상태와 `statusReason`이 바뀌면 양쪽 참여자에게 실시간으로 전달한다.
  - 요청·지원 상태와 임무 완료 확인 여부가 바뀌면 양쪽 참여자에게 실시간으로 전달한다. 앱은 이 값으로 상태 배지와 채팅방 안의 버튼(지원 취소, 매칭, 임무 완료)을 갱신한다.
  - 상대방의 읽음 위치가 바뀌면 실시간으로 전달한다. 앱은 이 값으로 안읽음 표시(`1`)를 지운다 (CHAT-REQ-013).
  - 자신의 안읽음 수와 전체 안읽음 합계가 바뀌면 실시간으로 전달한다.
  - 차단하거나 차단을 해제하면 양쪽 참여자에게 실시간으로 전달한다. 앱은 이 값으로 입력창을 막거나 다시 연다.
  - 연결이 끊긴 동안 바뀐 상태는 재연결 시 최신 상태로 확인할 수 있다 (CHAT-REQ-016).

#### CHAT-REQ-018 — 채팅 푸시 알림

- **Who:** 행님, 꼬붕
- **When:** 자신이 참여한 채팅방에 상대방의 일반 채팅이나 시스템 채팅이 저장되었을 때
- **What:**
  - 서버는 실시간 연결 여부와 관계없이 항상 FCM 푸시 알림을 보낸다.
  - 앱이 켜져 있을 때 푸시를 어떻게 보여줄지는 앱이 정한다. 해당 채팅방을 보고 있으면 표시하지 않고, 앱의 다른 화면에 있으면 앱 안에 배너로 보여준다. 앱이 꺼져 있거나 백그라운드면 시스템 푸시로 보여준다.
  - 자신이 보낸 채팅은 푸시하지 않는다.
  - 지원 등록 이후 사건은 기존 알림을 새로 만들지 않고 시스템 채팅으로 저장·푸시한다. 기존 알림 수신자도 시스템 푸시 대상에 포함한다(CHAT-REQ-030). 시스템 채팅별 푸시 대상은 CHAT-REQ-021 표를 따른다.
  - 푸시의 제목은 상대방 이름, 내용은 채팅 내용으로 한다. 탈퇴한 상대는 `"탈퇴한 사용자"`로 보여준다. 시스템 채팅의 푸시는 기존 알림 제목이 있으면 그 제목(`systemTitle`), 없으면 상대방 이름을 사용한다. 내용은 받는 사람에게 보이는 시스템 채팅 본문이다.
  - 같은 채팅방의 푸시는 하나로 묶는다. 새 채팅이 오면 이전 푸시를 대체하고 가장 최근 채팅 내용을 보여준다.
  - 앱 아이콘 배지 숫자는 채팅 전체 안읽음 합계(CHAT-REQ-011)와 알림 미읽음 수를 더한 값으로 한다. 채팅 푸시와 기존 알림 푸시 모두 이 값을 배지로 보낸다.
  - 푸시를 누르면 해당 채팅방으로 이동한다.
  - 채팅 푸시는 기존 알림 목록(`notifications`)에 저장하지 않는다. 채팅 기록은 채팅으로만 남기며, 알림 미읽음 수와 채팅 안읽음 수는 따로 센다.
  - 수신자의 알림 설정(`alarm_enabled`)이 꺼져 있으면 푸시를 보내지 않는다. 채팅 저장과 안읽음 수는 알림 설정과 관계없다.
  - 푸시 발송에 실패해도 채팅 저장에는 영향을 주지 않는다.
  - 푸시 발송이 실패하면 최대 5회 다시 보낸다(CHAT-REQ-029). 같은 채팅의 푸시는 성공 기준으로 한 번만 보낸다.
  - 채팅이 저장된 지 10분이 지난 푸시는 다시 보내지 않는다. 늦게 온 푸시는 이미 읽었거나 지난 내용이라 혼란만 준다. 그 채팅은 채팅방에 남아 있다.

### 6. 시스템 채팅

#### CHAT-REQ-020 — 시스템 채팅 생성

- **Who:** 서버
- **When:** 요청(Proposal), 지원(Offer), 임무(Mission), 정산·환불과 관련된 주요 사건이 확정되었을 때
- **What:**
  - 서버는 [사건별 시스템 채팅](#chat-req-021--사건별-시스템-채팅) 표에 정한 사건이 확정되면 해당 채팅방에 시스템 채팅을 자동으로 저장한다. 사건 처리가 실패하면 시스템 채팅도 저장하지 않는다.
  - 시스템 채팅은 일반 채팅과 구분할 수 있다.
  - 시스템 채팅에는 발생 사건, 내용, 생성 시각을 기록한다.
  - 시스템 채팅은 서버만 만들 수 있다. 행님과 꼬붕은 시스템 채팅을 만들거나 수정할 수 없다. 채팅 전송 요청은 채팅 유형을 받지 않으며, 정해지지 않은 필드가 담긴 요청은 거부한다.
  - 같은 사건의 시스템 채팅은 채팅방마다 하나로 저장하고, 받는 사람에 맞는 문구로 보여준다.
  - 같은 사건이 여러 번 전달되어도 시스템 채팅은 한 번만 저장한다.
  - 채팅방이 `INACTIVE` 또는 `CLOSED` 상태이거나 차단 중이어도 시스템 채팅을 저장한다.
  - 시스템 채팅의 내용은 안내일 뿐이며, 실제 정산·환불 상태는 별도로 관리한다.

- 지원 등록 안내는 꼬붕의 첫 인사(CHAT-REQ-006)보다 먼저 저장한다. 채팅 배포 때 기존 지원으로 만드는 채팅방에는 저장하지 않는다.
- 관리자의 게시글 신고 승인은 시스템 채팅을 저장하지 않는다. 대기 지원의 채팅방은 CHAT-REQ-007에 따라 `CLOSED`가 되어 채팅 전송만 막힌다.

#### CHAT-REQ-022 — 시스템 채팅 조회 및 읽음 처리

- **Who:** 행님, 꼬붕
- **When:** 시스템 채팅이 저장되었거나 사용자가 채팅방을 볼 때
- **What:**
  - 시스템 채팅은 일반 채팅과 같은 채팅 내역에서 저장 순서대로 함께 조회한다 (CHAT-REQ-004).
  - 시스템 채팅의 실시간 전달은 CHAT-REQ-015, 읽음 처리와 안읽음 수는 CHAT-REQ-010 ~ CHAT-REQ-012를 따른다. 안읽음 제외 대상은 CHAT-REQ-021 표를 따른다.
  - 채팅방이 종료되어도 시스템 채팅은 유지되며 조회할 수 있다 (CHAT-REQ-005).

### 7. 중복 요청 및 동시성 처리

1~6번의 요구사항이 요청이 겹치거나 순서가 뒤바뀌어도 지켜지도록 하는 규칙을 모은다. 각 요구사항에 이미 적힌 규칙은 다시 쓰지 않고 가리킨다.

#### CHAT-REQ-019 — 채팅 중복 전송 방지

- **Who:** 행님, 꼬붕
- **When:** 앱이 응답을 받지 못해 같은 채팅 전송을 다시 시도했을 때
- **What:**
  - 앱은 채팅을 보낼 때마다 고유한 전송 ID를 함께 보낸다. 재시도할 때는 같은 전송 ID를 다시 보낸다.
  - 같은 사용자가 같은 전송 ID로 여러 번 요청해도 채팅은 한 번만 저장된다.
  - 재시도 요청에도 처음 저장된 채팅으로 응답한다. 상대방에게 실시간 전달과 푸시도 한 번만 보낸다.
  - 같은 전송 ID로 내용이나 채팅방이 다른 요청이 오면 거부한다.
  - 첫 인사(CHAT-REQ-006)는 지원 등록과 함께 저장되므로 지원 등록의 중복 방지(CHAT-REQ-023)를 따른다.

#### CHAT-REQ-023 — 채팅방 중복 생성 방지

- **Who:** 서버
- **When:** 같은 지원 등록 요청이 동시에 여러 번 들어오거나, 채팅 배포 때 기존 지원의 채팅방을 만드는 중에 새 지원이 들어왔을 때
- **What:**
  - 지원 1건당 채팅방은 1개만 만들어진다 (CHAT-REQ-001). 같은 꼬붕이 같은 요청에 동시에 여러 번 지원해도 지원과 채팅방은 각각 1개만 남는다.
  - 지원 등록, 채팅방 생성, 지원 등록 시스템 채팅, 첫 인사 저장은 함께 성공하거나 함께 실패한다. 하나라도 실패하면 아무것도 남지 않는다.
  - 중복으로 거부된 지원 요청은 시스템 채팅이나 첫 인사를 남기지 않는다.
  - 채팅 배포 때 기존 지원의 채팅방을 만드는 작업은 여러 번 실행해도 채팅방이 한 번만 만들어진다. 이미 채팅방이 있는 지원은 건너뛴다.

#### CHAT-REQ-024 — 채팅 저장 순서

- **Who:** 서버
- **When:** 같은 채팅방에 채팅이 동시에 저장될 때
- **What:**
  - 같은 채팅방의 채팅(일반 채팅, 시스템 채팅)은 서버가 정한 하나의 저장 순서를 갖는다. 전송 시각이 같아도 순서는 하나로 정해진다.
  - 채팅 조회(CHAT-REQ-004), 실시간 전달(CHAT-REQ-015), 놓친 채팅 복구(CHAT-REQ-016), 읽음 위치(CHAT-REQ-010)는 모두 이 저장 순서를 기준으로 한다.
  - 앱이 마지막으로 받은 채팅 이후를 조회할 때, 그보다 앞 순서인데 늦게 저장이 끝난 채팅 때문에 빠지는 채팅이 없어야 한다.
  - 시스템 채팅은 사건이 확정된 순서대로 저장된다. 예를 들어 한쪽 임무 완료 안내는 양측 임무 완료 안내보다, 양측 임무 완료 안내는 입금 완료 안내보다 앞선다.
  - 채팅방을 종료하는 시스템 채팅 뒤에는 일반 채팅이 저장되지 않는다.

#### CHAT-REQ-025 — 채팅 전송과 상태 변경이 겹칠 때

- **Who:** 서버
- **When:** 채팅 전송과 채팅방 상태 변경(`INACTIVE`, `CLOSED`) 또는 차단이 동시에 일어났을 때
- **What:**
  - 전송과 상태 변경 중 먼저 확정된 쪽을 기준으로 처리한다. 상태 변경이 먼저 확정되면 전송을 거부하고, 전송이 먼저 확정되면 채팅은 저장되고 그 뒤에 상태가 바뀐다 (CHAT-REQ-009).
  - 거부된 전송은 채팅을 남기지 않으며, 앱은 거부 응답과 바뀐 채팅방 상태를 받는다.
  - 차단이 먼저 확정된 뒤의 전송도 같은 방식으로 거부한다.

#### CHAT-REQ-026 — 요청·지원 상태가 동시에 바뀔 때

- **Who:** 서버
- **When:** 채팅방 상태를 바꾸는 요청·지원 동작이 동시에 일어났을 때
- **What:**
  - 아래처럼 서로 겹치는 동작은 하나의 결과로만 확정된다. 채팅방 상태와 시스템 채팅은 확정된 결과만 따른다.
    - 행님이 여러 꼬붕을 동시에 매칭하면 한 명만 매칭된다. 매칭된 채팅방 1개만 `ACTIVE`로 남고 나머지는 `CLOSED`가 된다.
    - 매칭과 꼬붕의 지원 취소가 동시에 일어나면 둘 중 하나만 확정된다. 매칭 안내와 지원 취소 안내가 같은 채팅방에 함께 남지 않는다.
    - 매칭과 행님의 요청 취소, 매칭과 관리자 취소가 동시에 일어나도 둘 중 하나만 확정된다.
    - 꼬붕의 임무 완료와 행님의 임무 완료 확인이 동시에 일어나면 양측 임무 완료로 한 번만 확정된다. 채팅방은 한 번만 `CLOSED`가 되고 양측 임무 완료 안내는 한 번만 저장된다. 이때 한쪽 임무 완료 안내는 확정된 순서대로 남는다.
    - 임무 완료와 분쟁 접수가 동시에 일어나면 둘 중 먼저 확정된 쪽을 기준으로 하고, 뒤의 동작은 바뀐 상태에서 허용될 때만 처리한다.
  - 채팅방 상태 변경은 그 원인이 된 요청·지원·임무 상태 변경, 시스템 채팅 저장과 함께 성공하거나 함께 실패한다.
  - 채팅방 상태는 [채팅방 상태](#채팅방-상태) 표에서 허용한 방향으로만 바뀐다. `CLOSED`가 된 채팅방은 늦게 도착한 요청 때문에 `ACTIVE`나 `INACTIVE`로 돌아가지 않는다.

#### CHAT-REQ-027 — 읽음과 안읽음 수의 동시 처리

- **Who:** 서버
- **When:** 같은 사용자의 읽음 요청이 동시에 들어오거나, 읽음 요청과 새 채팅 저장이 겹쳤을 때
- **What:**
  - 같은 채팅방에 읽음 요청이 동시에 들어오면 가장 뒤의 채팅까지 읽은 것으로 남는다. 앞선 요청이 늦게 처리되어도 읽음 위치는 뒤로 돌아가지 않는다 (CHAT-REQ-010).
  - 읽음 요청에 담긴 채팅보다 뒤에 저장된 채팅은 안읽음으로 남는다. 채팅방 입장과 새 채팅 저장이 겹쳐도, 앱이 받지 못한 채팅을 읽음 처리하지 않는다.
  - 전체 읽음 처리 중에 저장된 채팅은 읽음 처리하지 않는다 (CHAT-REQ-012).
  - 안읽음 수는 읽음 위치와 저장된 채팅으로 정해지는 값이다 (CHAT-REQ-011). 요청이 겹쳐도 이 정의와 다른 값이 남지 않는다.
  - 푸시의 배지 숫자는 발송 시점의 값이다. 푸시가 늦게 도착해 배지가 실제와 다를 수 있으며, 앱은 열릴 때 서버의 안읽음 합계와 알림 미읽음 수로 배지를 다시 맞춘다.

#### CHAT-REQ-028 — 실시간 이벤트의 중복과 순서

- **Who:** 서버, 앱
- **When:** 실시간 이벤트가 중복으로 오거나, 보낸 순서와 다르게 도착했을 때
- **What:**
  - 같은 채팅이 실시간 전달과 재연결 복구로 겹쳐 와도 앱은 채팅 ID로 한 번만 보여준다 (CHAT-REQ-015, CHAT-REQ-016).
  - 채팅방 상태, 요청·지원 상태, 읽음 위치, 차단 상태 이벤트(CHAT-REQ-017)에는 순서를 판단할 수 있는 값을 담는다. 앱은 이미 반영한 것보다 오래된 이벤트가 늦게 도착하면 무시한다.
  - 상대방의 읽음 위치가 앞으로 돌아간 값으로 도착해도 앱은 이미 지운 안읽음 표시(`1`)를 다시 보여주지 않는다.
  - 같은 채팅이나 같은 시스템 채팅에 대한 푸시는 재시도가 있어도 한 번만 보낸다 (CHAT-REQ-018, CHAT-REQ-029).

#### CHAT-REQ-029 — 이벤트 전달 보장

- **Who:** 서버
- **When:** 채팅 저장, 채팅방 상태 변경, 읽음 변경처럼 앱에 실시간 이벤트나 푸시를 보내야 하는 변경이 확정되었을 때
- **What:**
  - 이벤트 전달은 공통 정책 [`event-delivery.md`](./event-delivery.md)(`OUTBOX-REQ-*`)를 따른다. 변경과 같은 트랜잭션에 기록하고, 서버가 멈춰도 다시 보내며, 실패하면 정책대로 다시 시도하고, 같은 이벤트를 같은 전달 대상에 두 번 처리하지 않는다.
  - 채팅의 전달 대상은 실시간(`chat.realtime`)과 푸시(`chat.push`) 두 가지다. 둘은 서로의 실패에 영향을 받지 않는다. 푸시가 실패해도 실시간 전달은 끝난 것으로 남고, 푸시만 다시 시도한다.
  - 실시간 전달은 다시 시도하지 않는다. 받는 사람이 연결되어 있지 않거나 보내다 실패하면 건너뛰고, 앱은 재연결 후 REST로 복구한다(CHAT-REQ-016).
  - 푸시는 최대 5회 다시 시도한다(5초, 30초, 1분, 2분, 4분 간격). 채팅이 저장된 지 10분이 지나면 건너뛴다. 5회 모두 실패하면 `DEAD`로 남기고 모니터링 알림을 보낸다. 관리자가 다시 처리해도 10분이 지났으면 건너뛴다.
  - 같은 채팅방의 이벤트는 기록된 순서대로 보낸다.

## 비기능 요구사항

### 성능

- 두 참여자가 모두 실시간 연결된 상태에서, 한쪽이 보낸 채팅은 1초 이내에 상대방 화면에 보여야 한다.
- 채팅 내역은 한 번에 30개씩 조회한다 (CHAT-REQ-004).

### 신뢰성 (채팅 유실·중복·순서)

- 유실: 서버는 저장에 성공한 채팅만 전달하며, 실시간 전달이나 푸시가 실패해도 저장된 채팅은 재연결 복구로 받을 수 있다 (CHAT-REQ-015, CHAT-REQ-016).
- 중복: 같은 전송 재시도와 같은 사건은 한 번만 저장되고, 앱은 채팅 ID로 중복 전달을 걸러낸다 (CHAT-REQ-019, CHAT-REQ-020, CHAT-REQ-028).
- 순서: 채팅방마다 서버가 정한 하나의 저장 순서를 기준으로 조회·복구·읽음 처리한다 (CHAT-REQ-024).
- 상태 일관성: 채팅방 상태, 시스템 채팅, 요청·지원·임무 상태는 함께 성공하거나 함께 실패한다 (CHAT-REQ-026).
- 전달 보장: 보낼 이벤트를 변경과 같은 트랜잭션에 기록하고, 실패하면 다시 시도하며, 같은 이벤트를 두 번 처리하지 않는다 (CHAT-REQ-029).

### 보안·개인정보

- 채팅방 참여자가 아닌 사용자는 채팅 내역, 실시간 채팅, 푸시를 받을 수 없다. 기존 API와 같이 `403 FORBIDDEN`을 반환한다 (CHAT-REQ-002, CHAT-REQ-015).
- 실시간 연결도 기존 API와 같은 access token으로 인증하고, 재연결 때마다 인증과 참여 권한을 다시 확인한다 (CHAT-REQ-016).
- 관리자는 관리자 웹에서 채팅을 조회만 할 수 있다. 관리자 열람 기록은 남기지 않는다.
- 회원 탈퇴 후에도 채팅 내용은 유지하고 이름만 `"탈퇴한 사용자"`로 바꾼다 (CHAT-REQ-005).
- 채팅 기록 보관 기한은 정하지 않으며 후속 작업으로 둔다 ([범위](#제외)).

#### CHAT-REQ-030 — 지원 이후 안내 통합

2026-11-18 변경 정본은 [NOTI-REQ-001](./notification-policy.md#noti-req-001--지원-전후-전달-정책)이다. 기존 알림과 시스템 채팅을 중복 생성하지 않는다. 기존 알림 수신자에게도 시스템 푸시를 보내며 기존 제목·본문을 정확하게 유지한다. 조회/실시간 응답의 `systemTitle`은 기존 알림 제목(없으면 null), `content`는 수신자별 본문이다. 매칭 전 환불도 지원 이력이 있으면 기존 채팅방들에 기록한다. 요청 만료 안내는 TD-021에 보류한다.
