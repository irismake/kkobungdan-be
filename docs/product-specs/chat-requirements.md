## 채팅방 상태

채팅을 보낼 수 있는지를 표현한다. 임무가 어떤 단계에 있는지는 요청·지원 상태가 표현하므로 채팅방은 이를 중복해서 갖지 않는다.

| 상태 | 의미 | 메시지 전송 | 다시 활성화 |
|------|------|-------------|-------------|
| `ACTIVE` | 채팅을 주고받을 수 있는 상태 | 가능 | — |
| `INACTIVE` | 일시적으로 채팅을 보낼 수 없는 상태. 이후 `ACTIVE` 또는 `CLOSED`가 될 수 있다 | 불가 | 가능 |
| `CLOSED` | 채팅이 끝난 상태 | 불가 | 불가 |

- 채팅방 상태는 미션 변화로만 바뀐다. `INACTIVE`가 되는 경우는 현재 분쟁 접수뿐이며, 분쟁 판정이 나면 `CLOSED`가 된다. `INACTIVE`에서 `ACTIVE`로 돌아가는 경우는 아직 없고 확장을 위해 둔다.
- 사용자 차단은 채팅방 상태에 반영하지 않고 [사용자 차단 상태](#사용자-차단-상태)로 따로 관리한다. 두 정보는 서로 바꾸지 않는다.
- 메시지는 채팅방이 `ACTIVE`이고 차단이 없을 때만 보낼 수 있다. 서버는 이 조건으로 전송을 거부한다. 전송 가능 여부를 합친 별도 필드는 두지 않으며, 앱은 채팅방 상태와 차단 여부를 함께 보고 판단한다.
- 채팅방 상태는 메시지 전송만 제어한다. 지원 취소, 매칭, 임무 완료, 분쟁 접수 같은 임무 동작은 채팅방 상태와 관계없이 요청·지원 상태로 허용 여부를 판단한다. 예를 들어 상대를 차단한 상태에서도 임무 완료를 확인할 수 있다.
- 앱의 상태 배지와 채팅방 안의 버튼(지원 취소, 매칭, 임무 완료)은 채팅방 상태가 아니라 요청·지원 상태로 표시한다. 채팅방 응답에 요청·지원 상태를 함께 담는다.

### 상태 이유 (`statusReason`)

같은 상태라도 앱에 보여줄 내용이 다르면 상태를 늘리지 않고 `statusReason`으로 구분한다.

| 상태 | statusReason | 경우 |
|------|--------------|------|
| `ACTIVE` | `null` | 지원 등록 후 매칭 대기, 매칭 후 임무 진행 중 |
| `INACTIVE` | `ORDERER_DISPUTED` | 행님이 분쟁을 접수함 |
| `INACTIVE` | `RUNNER_DISPUTED` | 꼬붕이 분쟁을 접수함 |
| `CLOSED` | `NOT_SELECTED` | 행님이 다른 꼬붕을 매칭함 |
| `CLOSED` | `OFFER_CANCELLED` | 꼬붕이 지원을 취소함 |
| `CLOSED` | `OFFER_CANCELLED` | 꼬붕이 회원 탈퇴하여 대기 중인 지원이 자동 취소됨 |
| `CLOSED` | `PROPOSAL_CANCELLED` | 행님이 매칭 전에 요청을 취소함 |
| `CLOSED` | `ADMIN_CANCELLED` | 관리자가 매칭 전에 요청을 취소함 |
| `CLOSED` | `ADMIN_CANCELLED` | 관리자가 게시글 신고를 승인함 (요청 `REPORTED`) |
| `CLOSED` | `ADMIN_CANCELLED` | 관리자가 매칭 후 요청을 취소함 |
| `CLOSED` | `ALL_CONFIRMED` | 행님과 꼬붕이 모두 임무 완료를 확인함 |
| `CLOSED` | `DISPUTE_COMPLETED` | 분쟁 판정 결과 행님 책임 (미션 `COMPLETED`) |
| `CLOSED` | `DISPUTE_FAILED` | 분쟁 판정 결과 꼬붕 책임 (미션 `FAILED`) |

- 임무 진행 상황(한쪽만 완료 확인 등)은 채팅방 이유로 표현하지 않는다. 지원 상태와 완료 확인 시각으로 알 수 있다.
- 환불 대기·완료는 채팅방 이유로 표현하지 않는다. 요청 상태(`REFUND_PENDING`, `REFUNDED`) 배지로 보여준다.
- 탈퇴한 상대의 이름은 기존 앱 응답과 같이 `"탈퇴한 사용자"`로 내려준다. 탈퇴는 `statusReason`으로 구분하지 않는다.

## 사용자 차단 상태

해당 사용자가 상대방을 차단했는지를 사용자 사이의 관계로 기록한다. 채팅방 상태와 별도로 관리하며 채팅방 상태를 바꾸지 않는다.

| 상태 |
|------|
| 차단하지 않음 |
| 차단함 |

- 차단은 채팅방 단위가 아니라 사용자 단위다. 차단하면 그 사용자와의 모든 채팅방에서 메시지를 보낼 수 없으며, 이후 새로 생기는 채팅방에도 적용된다.
- 한쪽이 차단하면 양쪽 모두 메시지를 보낼 수 없다.
- 차단은 차단한 사람만 해제할 수 있다. 해제하면 차단 기록만 바뀌고 채팅방 상태는 바뀌지 않는다.
- 채팅방 응답에는 차단 여부(차단 안 함 / 내가 차단함 / 상대가 차단함)를 함께 담는다.

## 기능 요구사항

카테고리는 요구사항 분류용이며 작업 단위가 아니다.

### 1. 채팅방 생성 및 참여 권한

#### CHAT-REQ-001 — 채팅방 생성

- **Who:** 꼬붕
- **When:** 행님의 임무(Proposal)에 꼬붕이 지원(Offer)을 정상 등록했을 때
- **What:**
  - Offer 1건당 채팅방 1개를 자동 생성한다.
  - 채팅방은 해당 임무의 행님과 지원한 꼬붕, 총 2명으로 구성된다.
  - 하나의 임무에 여러 꼬붕이 지원했다면 꼬붕별로 독립적인 채팅방을 생성한다.
  - 동일한 꼬붕은 하나의 임무에 한 번만 지원할 수 있으므로, 동일한 행님과 꼬붕 사이에 같은 임무에 대한 채팅방은 1개만 생성된다.
  - 지원 취소 후 같은 임무에 다시 지원할 수 없으므로, 같은 임무에 대한 채팅방도 다시 생성되지 않는다.
  - 동일한 두 명의 사용자라도 서로 다른 임무에 대한 지원이라면 각각 별도의 채팅방을 생성할 수 있다.
  - 채팅방 생성 시 초기 상태는 `ACTIVE`이다.

#### CHAT-REQ-002 — 채팅방 접근 권한

- **Who:** 행님, 꼬붕
- **When:** 채팅방에 접근하거나 채팅 목록을 조회할 때
- **What:**
  - 행님은 자신이 등록한 임무에 지원한 모든 꼬붕의 채팅방에 접근할 수 있다.
  - 꼬붕은 자신이 지원한 임무의 채팅방에만 접근할 수 있다.
  - 채팅방 참여자가 아닌 제3자는 접근할 수 없다. 기존 API와 같이 `403 FORBIDDEN`을 반환한다.
  - 채팅방이 종료되거나 상대방을 차단한 이후에도 기존 참여자의 채팅방 조회 권한은 유지된다.
  - 관리자는 관리자 웹에서 모든 채팅방의 채팅 내용을 조회할 수 있다. 관리자는 채팅을 전송할 수 없고, 관리자의 조회는 참여자의 읽음 상태를 바꾸지 않는다.

### 2. 채팅 전송 및 조회

#### CHAT-REQ-003 — 채팅 전송

- **Who:** 행님, 꼬붕
- **When:** 채팅방이 `ACTIVE` 상태일 때
- **What:**
  - 채팅방 참여자는 텍스트 채팅을 전송할 수 있다.
  - 전송된 채팅은 서버에 저장한다.
  - 채팅에는 발신자, 내용, 전송 시각을 기록한다.
  - 채팅은 해당 채팅방의 행님과 꼬붕만 주고받을 수 있다.
  - 일반 채팅은 최대 500자까지 입력할 수 있다.
  - 글자 수는 화면에 보이는 글자 단위(grapheme cluster)로 센다. 앱(Swift `String.count`)과 같은 기준이며, 첫 인사(CHAT-REQ-006)에도 같은 기준을 적용한다.
  - 전송 시각은 기존 API와 같이 UTC로 응답한다.

#### CHAT-REQ-004 — 채팅 조회

- **Who:** 행님, 꼬붕
- **When:** 자신이 참여한 채팅방에 접근했을 때
- **What:**
  - 해당 채팅방에 저장된 채팅 내역을 조회할 수 있다.
  - 채팅은 전송된 순서대로 조회할 수 있다.
  - 이전 채팅 내역을 추가로 조회할 수 있다.
  - 각 채팅의 발신자, 내용, 전송 시각을 확인할 수 있다.

#### CHAT-REQ-005 — 채팅 기록 유지

- **Who:** 행님, 꼬붕
- **When:** 채팅방 상태가 변경되거나 상대방을 차단했을 때
- **What:**
  - 채팅방이 `INACTIVE` 또는 `CLOSED` 상태로 변경되어도 기존 채팅 기록을 유지한다.
  - 상대방을 차단하거나 차단당하더라도 기존 채팅 기록을 조회할 수 있다.
  - 채팅 전송이 제한된 상태에서도 기존 채팅 기록은 조회할 수 있다.

#### CHAT-REQ-006 — 지원 시 첫 인사 채팅

- **Who:** 꼬붕
- **When:** 행님의 임무(Proposal)에 지원(Offer)을 등록했을 때
- **What:**
  - 꼬붕이 지원 시 작성한 첫 인사를 해당 채팅방에 자동 저장한다.
  - 첫 인사는 꼬붕이 전송한 일반 채팅으로 저장한다.
  - 첫 인사는 필수 입력이다.
  - 첫 인사는 최대 500자까지 입력할 수 있다. 글자 수 기준은 CHAT-REQ-003과 같다.
  - 지원 등록과 첫 인사 저장은 함께 성공하거나 실패해야 한다.

### 3. 요청 상태에 따른 채팅 제어

#### CHAT-REQ-007 — 채팅방 상태 변경

- **Who:** 서버
- **When:** 요청(Proposal) 또는 지원(Offer)의 상태가 변경되었을 때
- **What:**
  - 지원 등록 시 채팅방을 `ACTIVE` 상태로 생성한다.
  - 행님이 꼬붕을 선택하여 매칭하면 해당 채팅방은 `ACTIVE`를 유지한다.
  - 매칭되지 않은 다른 꼬붕의 채팅방은 `CLOSED`로 변경한다.
  - 꼬붕이 지원을 취소하거나 행님이 요청을 취소하면 해당 채팅방을 `CLOSED`로 변경한다.
  - 관리자가 요청을 취소하면 `CLOSED`가 아닌 채팅방을 `CLOSED`로 변경한다. 단, 분쟁 중인 요청은 관리자 취소 대상에서 제외한다.
  - 관리자가 게시글 신고를 승인하여 요청이 `REPORTED` 상태가 되면, 거절 처리된 대기 지원의 채팅방을 `CLOSED`로 변경한다.
  - 꼬붕이 회원 탈퇴하여 대기 중인 지원이 자동 취소되면 해당 채팅방을 `CLOSED`로 변경한다.
  - 행님과 꼬붕이 모두 임무 완료를 확인하면 `CLOSED`로 변경한다.
  - 분쟁이 접수되면 해당 채팅방을 `INACTIVE`로 변경한다.
  - 관리자가 분쟁을 판정하면 `INACTIVE` 상태를 `CLOSED`로 변경한다.
  - 상태와 함께 바뀌는 `statusReason`은 [상태 이유](#상태-이유-statusreason) 표를 따른다.

#### CHAT-REQ-008 — 임무 완료 처리

- **Who:** 행님, 꼬붕
- **When:** 매칭되어 임무가 진행 중일 때 (지원 `ACCEPTED` 또는 `RUNNER_COMPLETED`)
- **What:**
  - 행님과 꼬붕은 각각 임무 완료를 확인할 수 있다. 채팅방 상태나 차단 여부와 관계없이 가능하다.
  - 한쪽만 완료를 확인한 경우 채팅방 상태는 바뀌지 않는다.
  - 양쪽 모두 완료를 확인하면 채팅방을 `CLOSED`로 변경한다.
  - 이미 완료를 확인한 사용자는 중복으로 완료 처리할 수 없다.

#### CHAT-REQ-009 — 채팅 전송 제한

- **Who:** 행님, 꼬붕
- **When:** 채팅방이 `INACTIVE` 또는 `CLOSED` 상태일 때
- **What:**
  - 새로운 채팅을 전송할 수 없다.
  - 채팅방 상태가 변경된 이후에는 이전 상태를 기준으로 새로운 채팅을 저장할 수 없다.
  - 채팅 전송이 제한되어도 기존 채팅 내역은 조회할 수 있다.
  - 사용자 차단에 따른 채팅 전송 제한은 [사용자 차단 상태](#사용자-차단-상태) 규칙을 따른다.

| 지원 등록 API (`POST` Offer, `OfferCreate`) | 꼬붕이 지원할 때 첫 인사 메시지를 필수로 받는 필드 추가. 현재는 `proposalId`만 받고 다른 필드를 거부한다(`extra="forbid"`). 필수이므로 서버 배포 후 첫 인사를 보내지 않는 기존 앱의 지원은 실패한다. 앱 배포와 순서를 맞춰야 한다 | 채팅 구현 시 함께 | CHAT-REQ-006 |

## 미결정 사항

- 차단 (별도 브랜치에서 결정)
  - 차단당한 꼬붕이 차단한 행님의 요청에 지원할 수 있는지. 허용하면 메시지를 보낼 수 없는 채팅방에 필수 첫 인사가 저장된다.
  - 차단한 상대의 채팅방·요청·지원을 목록에서 숨길지
  - 차단한 사용자(또는 차단당한 사용자)의 지원을 매칭할 수 있는지. 임무 동작은 채팅방 상태와 무관하므로 별도 정책이 없으면 매칭이 가능하다
